## 1. 结构性问题（影响最大，先改）

### 1.1 没有"30 秒电梯层"

企业级 README 按读者分三层设计：

| 读者 | 停留时间 | 该看到什么 | 当前状态 |
|---|---|---|---|
| HR / 面试官 | 30 秒 | 是什么 + **量化成果** + 一张截图 | ❌ 成果埋在第 260 行 |
| 工程师 | 3 分钟 | 架构 + Quick Start + 能力 | ✅ 有但淹没 |
| 深度评审 | 10 分钟 | 评测口径 + 设计决策 + 限制 | ✅ 有 |

**改法**：把评测章节的 KPI 表搬到第一屏。

**关键认知：负向指标前置是企业级自信信号。** `转人工 recall 0%（北极星基线首次量化）`、`意图准确率 62.5%（路由兜底后完成率未受累）` 这种"我知道我差在哪"的表述，比全绿指标更让评审信服——它证明评测体系真的在工作，且作者有工程成熟度。

### 1.2 Quick Start 9 个小节平铺 → 压成 3 步

现状：从"环境准备"到"界面设计系统"共 9 节，监控栈、坐席工作台、设计令牌全铺在启动路径上。

企业写法：

```
快速开始（3 步跑通核心）
  1. git clone + uv sync + cp .env.example .env
  2. alembic upgrade head + seed + ingest
  3. uvicorn 或 docker compose up

可选组件（每项 3-5 行 + 一条启动命令）
  监控栈 / 追踪栈 / 坐席工作台 / 对话界面 / 评测台 / 设计系统
```

### 1.3 加 TOC

360 行长文档，GitHub 锚点目录是标配，放徽章行下方。

## 2. 数字纪律（硬伤，半天内必须修）

逐项核对结果——**三处矛盾/过期**，面试官发现一处对不上就会对所有数字失去信任：

| README 位置 | 写的 | 实际 |
|---|---|---|
| 技术栈表 | pytest 391 用例 | tests/ 下 **467** 个 test 函数 |
| 测试与验证章节 | 367 用例全绿 | 同上，过期 |
| 项目结构 | tests/ 367 个测试用例 | 同上 |
| 项目结构 | evals 218+84 条 | 专项实为 **218+74**（graph_assoc 24 + multiturn 30 + adversarial 20） |

两种解法：

- **治本**：数字不写死正文——用 CI 动态徽章（pytest 数量 / coverage），或标注"以 `pytest --collect-only` 为准"
- **治标**：改完跑一遍统一更新，并把"同步 README 数字"写进发布 checklist

## 3. 内外视角分离

### 3.1 内部任务编号收敛

`T049/D024`、`T037`、`D026` 是内部任务系统的坐标，外部读者不认识，且是"AI 生成未消化"的观感信号。全文 30+ 处。

企业级写法：正文只讲设计语言（"合规门禁由图结构保证，任何代码路径无法绕过"），编号收敛为一处链接：**"构建过程与全部决策记录见 `.agent/`"**。

### 3.2 能力大表 16 行 → 8 行以内

每行的实现细节（如 `Command(goto) + 计划对账，支持执行中重规划`）下沉到架构/设计要点章节；表格只留"能力 + 一句话价值"。

## 4. 缺失件清单（企业标配）

| 缺失 | 为什么必加 | 成本 |
|---|---|---|
| **License** | 无 License = 法务灰区；作品集加 MIT 防代码盗用顾虑 | 1 分钟 |
| **首屏截图 / GIF** | "眼见为实"是最高效说服；截图现散在 139/163 行深处 | 挪位置即可 |
| **Known Limitations 独立章** | 意图 62.5%、HITL recall 0%、Mock 边界现在藏在评测表里；独立成章 + Roadmap 才叫"已知问题管理" | 10 分钟 |

| **作者与联系方式** | 求职场景这是转化入口 | 2 分钟 |
| 徽章体系 | 现仅 CI 一个；建议 4-6 个：CI / Python 3.12 / License / ruff / tests | 10 分钟 |
