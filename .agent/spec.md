## 1. 问题陈述

多险种理赔案件人工审核成本高、周期长（件均数天），且各险种材料体系与核赔路径差异大，固定流程系统无法覆盖。本项目构建 **LLM Orchestrator-Worker 多智能体核赔平台**：受理期自动分类险种，Orchestrator 动态调度专业 Worker（材料审核/保单核验/风控筛查/责任认定/金额理算/决定书生成）完成自动核赔；领域知识以 skill 作业规程包承载；低风险小额案件自动签发《理赔决定书》，其余精准转人工。

> 定位：求职作品集，按真实业务 PoC 原型级别设计——审批流可审计、金额确定性、数据合规均按生产标准取舍，外部系统用可信 Mock 起步。

| 竞品 | 类型/定位 | 核心功能 | 对本项目的启示 |
|---|---|---|---|

## 3. 目标用户

- **C 端客户**：提交理赔申请与材料、按指引补件、查看进度与决定书
- **核赔坐席（内勤）**：复核签批、补件催办、升级处理（workbench 工作台）
- **运营/技术评审**：自动结案率、路由准确率、件均耗时、全链路审计回放

## 4. MVP 功能列表

> 每条功能必须有可验证的验收标准。不在此列表中的功能不做。

| 编号 | 功能名称 | 描述 | 验收标准 |
|------|---------|------|---------|
| F01 | 案件受理与幂等 | 提交案件（险种/保单/金额/事故描述/材料），按保单 product_type 确定性分类险种；重复提交幂等 | 重复 case 返回既有结论不重复执行；未上线险种转人工受理；受理记录落库 |
| F02 | 材料上传与解析 | 图片/PDF/Word 两段式提取（文本 → 扫描件 vision），Mock 兜底 | 真实材料字段提取正确；解析失败接口不报错走兜底 |
| F03 | Orchestrator 动态调度 | RoutingDecision 结构化输出 + 并行 Send 派发 + **前置条件守卫** + 失败兜底默认计划 + 决策审计落 case_events | 金样本路由一致率 ≥95%；守卫注入用例 100% 拦截；LLM 失败走兜底案件不阻塞；每案件调度调用 ≤15 |
| F04 | 材料审核 | OCR/解析 → 结构化抽取 → 完整性校验 → 补件流转 | 关键字段 F1 ≥95%；完整性规则纯函数单测全覆盖 |
| F05 | 保单核验 | 有效性/等待期/除外责任/限额核验（条款要素由 pack 提供） | 金样本判定一致；边界（过期/等待期内）单测 |
| F06 | 风控筛查 | 欺诈规则评分 + 黑名单 + 理赔频率（Mock） | 规则评分与金样本期望一致；高风险短路转人工 |
| F07 | 责任认定 | 确定性前置 + ReAct Agent + 关键词兜底三层，输出结论/条款引用/置信度 | 责任认定一致率 ≥90%；引用条款可溯源；LLM 不可用时关键词兜底仍出结论 |
| F08 | 金额理算 | 确定性计算（Decimal），扣减明细/部分责任/限额 | **金额正确率 100%**（错一分即挂）；无 LLM 参与 |
| F09 | 决定书生成 | 骨架代码渲染 + LLM 只写叙述段（不含金额）+ 版本化落库 | 要素齐备（结论/金额/依据/救济途径）；版本可追溯；叙述失败回退规则版 |
| F10 | 合规门（静态） | 三态 PASS/MODIFY/REJECT + 修订闭环 + **金额一致性断言** + PII 脱敏；decision_generate→合规门为静态边不可绕过 | 红线漏放 0；金额注入用例 100% 拦截；图结构断言证明无旁路 |
| F11 | 分级自动签发 | 低风险+责任明确+金额阈值内自动出书；否则转人工 | 金样本签发/转人工路由 ≥95%；阈值全部配置化 |
| F12 | HITL 人工介入 | SUPPLEMENT/REVIEW/ESCAPE 三类工单；interrupt 挂起 + Command(resume) 恢复 | 补件→材料审核重跑；签批→签发；REJECT→坐席结论过合规复审；跨服务重启可恢复 |
| F13 | 坐席工作台 | 工单类型筛选、案件时间线（含路由决策审计）、签批表单、补件上传 | 操作链路可用；npm build 通过 |
| F14 | 案件查询 | 进度/阶段结论/决定书/审计事件查询 API | API 单测；审计事件完整可回放 |
| F15 | 案件提交演示门户 | 提交 + 传材料 → 进度时间线 → 决定书查看/补件 | 全链路演示可走通；截图目检 |

## 5. 非目标（明确不做什么）

- **真实第三方系统对接**：保单/黑名单/医疗 API 为可信 Mock（PoC 单租户，替换真实接口见 `tools/README.md` 的 Adapter 约定）
- 电子签章、医保结算对接、影像智能审核
- 用户注册登录/多租户/权限体系（PoC 单租户；坐席端点用 `X-Staff-Key` 简单鉴权）
- 短信/小程序通知、监管报送导出
- 核赔跨会话长期记忆（业务无此需求；已实现的是「申请人历史档案」用于路由增强，默认关）

## 6. 边界与异常

> 每个 MVP 功能的异常路径与期望行为，E 编号供任务和测试引用。

| 编号 | 所属功能 | 异常场景 | 期望行为 |
|------|---------|---------|---------|
| E01 | F01 | 重复提交同一案件（user_id + policy_no + claimed_amount + incident_date 相同） | 返回既有结论，不重复执行；受理记录唯一约束保护 |
| E02 | F01 | 保单产品类型不在任何 pack（重疾险等） | 受理期转人工（escape），不进入核赔管线 |
| E03 | F01 | 无保单数据 | 回退客户自报险种，仍走确定性分类 |
| E04 | F02 | 材料解析失败 / 文件格式不支持 | 接口不报错，`_reference_document` 引用型兜底（doc_type 已知、无字段），材料审核继续 |
| E05 | F02 | 单份材料提取超时（>120s） | `@task` retry 2 次后仍失败 → fail-open 记 warning，该份降级为引用型，不阻塞案件 |
| E06 | F03 | LLM 路由决策失败 / 超预算 | 回退 `default_route` 确定性兜底编排（险种标准管线），案件不阻塞，审计记录兜底原因 |
| E07 | F03 | LLM 路由违规（必做集未完成就派发决定书） | `enforce_guards` 前置守卫 100% 改投；金样本守卫注入用例断言拦截 |
| E08 | F03 | 单案件调度调用超 15 次 | 预算门拦截并强制转 human，防绕圈 |
| E09 | F05 | 保单过期 / 等待期内出险 | 确定性前置直接判 not_covered，不进 LLM |
| E10 | F07 | LLM 不可用 / ReAct 超轮数 / 工具全超时 | 三层兜底：确定性前置 → ReAct → 关键词规则（除外关键词 + 自费金额识别），仍出结论 |
| E11 | F07 | 责任置信度 < floor（0.8） | 按设计转人工（fail-safe，T160 实测 17 例均为此路径），不硬判 |
| E12 | F08 | 关键字段（金额/诊断）缺失 | 提取置信度校准扣分：缺金额 0.65 < 自动签发门 0.8；缺双核心 0.4 < 转人工门 0.6 |
| E13 | F09 | LLM 叙述撰写失败 | 回退规则版叙述（fail-open），决定书要素仍齐备 |
| E14 | F10 | 坐席签批文本含红线内容 | 合规门复审 REJECT → 不签发，安全兜底转人工 |
| E15 | F10 | 决定书金额与理算结果不一致 | 金额三方断言拦截（正文/结构化数据/理算），MODIFY 修订闭环 |
| E16 | F12 | 补件期间进程重启 | Checkpoint 支撑 interrupt 恢复，thread_id = case_id |
| E17 | F12 | checkpoint 版本不匹配（代码更新后 resume 旧 thread） | 版本门卫删旧 checkpoint 重跑（T141），不报错 |
| E18 | F19 | 多实例同时认领同一 CaseJob | CAS + 租约（locked_by / lease_expires_at + 心跳续租 ttl/3），崩溃实例任务由租约到期接管 |
| E19 | F19 | dev 多实例未共享 checkpoint（默认进程内存） | 必须显式设 `CHECKPOINT_BACKEND=sqlite`，否则他实例认领 RESUME 后找不到 checkpoint 触发全新重跑（T145 实锤） |
| E20 | F20 | 记忆置信度 < 0.6 | 不写入（避免污染后续路由判断） |
| E21 | F17 | 供应商不返回缓存字段 / 指标提取失败 | 不记该维度（不臆造 0），主流程不受影响 |
| E22 | F18 | 客服检索未命中 / 用户要求转人工 | Agent 内 escalate 标记；问答门禁靠禁止词与转人工终态兜底 |

## 7. 技术约束

- Python 3.12（必须类型注解）；LangGraph 状态机 + Checkpoint；FastAPI async
- 部署在 Docker 容器内，`docker compose up -d` 一键启动；监控/追踪栈独立 profile 按需起
- **金额确定性**：全链路 Decimal 禁止 float；决定书金额与理算结果机器断言一致
- **可审计**：阶段结论与 orchestrator 路由决策 append-only 落库，案件全流程可回放
- **数据合规**：PII 脱敏输出；LLM 走可配置供应商（deepseek-flash）
- **性能**：单案件端到端 ≤3 分钟（P95，Mock 依赖下）；调度调用预算 ≤15 次/案件
- **配置化**：自动签发阈值 / 置信度门槛 / 轮数上限 / 调用预算全部进 pydantic-settings
- **测试**：核心业务逻辑必须有单测，外部 API 一律 mock；当前 528 passed

## 8. 假设与依赖

**假设**（访谈中未明确、按建议取值）：

- 用户已有 Docker Desktop 或可安装（容器化是一键启动的前提）
- `LLM_API_KEY` 由用户自行提供（DeepSeek OpenAI 兼容接口；无 Key 时材料提取走 Mock 兜底、其余 LLM 环节 fail-open）
- 单租户部署，不引入多租户隔离

**依赖**：

- **DeepSeek API**（deepseek-flash，原生多模态兼 vision）——可配置切换供应商（GLM 已接，A/B 变体见 `evals/variants.py`）
- **BGE-M3权重**（本地缓存，`hf_cache` 卷；CI 走 `download_bge_ci.py` 预热避免 huggingface.co 不可达）
- PostgreSQL / Qdrant / Redis（compose 单容器，非外部托管服务）
