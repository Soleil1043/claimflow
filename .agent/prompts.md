# Prompt 模板参考

> 每个阶段对应的 Prompt 模板，直接复制到任意 Agent 对话框使用。
> 将 `[占位符]` 替换为你的实际内容。

---

## Phase 1 — 需求定义

```
我要构建一个 [一句话描述项目]。

请先问我 3-5 个澄清问题（目标用户、核心功能、MVP 范围、技术约束），
等回答后，在 .agent/spec.md 中写：
1. 问题陈述：项目解决什么问题
2. 目标用户：谁会用
3. MVP 功能列表：每条附验收标准
4. 非目标：明确不做什么
5. 技术约束：必须满足的限制

写完让我确认，确认后再进入下一步。
```

## Phase 2 — 架构设计

```
读取 .agent/spec.md，设计技术架构。

在 .agent/plan.md 中写：
1. 技术选型：每个选择附一句理由
2. 目录结构：完整文件树
3. 数据模型：表名 + 字段 + 类型 + 约束 + 关系
4. API 设计：端点列表 + Method + 请求/响应格式
5. 第三方依赖：包名 + 版本 + 用途
6. 关键决策记录：同步写入 .agent/decisions.md

写完让我确认。
```

## Phase 3 — 任务拆解

```
读取 .agent/plan.md，拆解实现任务。

在 .agent/tasks.md 中写一个有序清单，格式：
- [ ] T0XX: [任务名] | 依赖: [T0XX或无] | 涉及文件: [路径] | 验收: [标准]

规则：
- 粒度：1 个任务 = 1 个可独立验证的功能点
- 依赖：标注前置任务编号
- 顺序：基础设施数据层 → 核心业务 → API → 辅助 → 测试 → 文档
- 验收：写明怎么验证（运行什么命令、看什么结果）

写完让我确认。
```

## Phase 4 — 逐任务构建（循环调用）

```
读取 .agent/tasks.md，实现下一个未完成的任务。

要求：
1. 只实现这一个任务，不要超前做后面的
2. 完成后在 tasks.md 中将 [ ] 改为 [x]
3. 在 progress.md 中追加记录（任务编号、文件变更、验证方式）
4. 单独 git commit
5. 告诉我验证方法，等我确认后再做下一个
```

## Phase 5 — 验证交付

```
所有任务已完成。进行最终验证：

1. 运行全部测试，修复所有报错
2. 逐条对照 .agent/spec.md，检查 MVP 功能是否全部实现
3. 检查 edge case（空输入、异常路径、权限边界）
4. 配置 CI 流水线（.github/workflows/ci.yml）：lint + test，push 自动触发
5. push 到 GitHub，确认 CI 全绿
6. （可选）配置 CD：main 分支合并后自动部署
7. 更新 README.md：安装步骤、运行方式、API 文档、CI 徽章
8. 在 progress.md 写最终总结

报告：已完成 / 有问题 / 下一步建议。
```

## 上下文恢复 Prompt

> 新会话或会话中断后，用这个 Prompt 让 Agent 快速恢复状态。

```
读取 .agent/ 目录下所有 .md 文件（spec.md, plan.md, tasks.md, progress.md, decisions.md），
理解当前项目状态。

报告：
1. 项目目标（来自 spec.md）
2. 已完成的任务（tasks.md 中 [x] 的项）
3. 下一个待执行的任务
4. 有无未解决的问题

等我确认后再继续执行。
```

## 回退 Prompt

> 某个任务出问题，需要回退时使用。

```
任务 [T0XX] 实现有问题，需要回退。

操作：
1. git reset 到 [T0XX] 之前的 commit
2. 在 tasks.md 中将 [T0XX] 改回 [ ]
3. 在 progress.md 中记录回退原因
4. 重新实现 [T0XX]，这次注意 [具体问题]
```

## 需求变更 Prompt

> 构建中要改功能/需求时使用。**先改规格，再改代码**，不直接动实现。

```
需求变更：[简述要改什么]

请按以下顺序处理，不要跳步：

1. **确认变更范围**：这次变更影响 spec.md 的哪几节（§4 功能列表 Fxx / §6 边界与异常 Exx /
   §7 技术约束 / §8 假设与依赖）？涉及哪些已有任务？
2. **修订 spec.md**：
   - §4 增删改 Fxx 条目（含验收标准）
   - §6 增删改 Exx 条目（含异常场景与期望行为）
   - **§9 变更记录追加一行**（版本 / 日期 / 变更内容 / 影响范围 / 状态），只追加不删
3. **同步下游**：plan.md（如涉及技术方案）、tasks.md（如涉及任务拆解）按新规格更新；
   已完成的受影响任务在 tasks.md 标注 `[ ]` 打回
4. **列出受影响任务清单**给用户确认，说明每个任务要改什么
5. 用户确认后才动代码，按任务逐个改（每次一个 commit）
```

## 设计变更 Prompt（架构/设计变动）

> 涉及技术栈、数据模型、模块结构、关键接口、第三方依赖的变动。**先算账再动手。**

```
设计变更：[简述要改什么设计]

请按以下顺序处理，不要跳步：

1. **优势与代价分析**（对话式，先说清再问）：
   - 收益：解决什么问题，带来什么改善
   - 风险：可能引入什么故障/回归
   - 影响范围：哪些模块/接口/数据会受影响，是否需要迁移
   - 迁移成本：改动量、是否需要数据迁移或停机
2. **列出至少 2 个可行方案**对比，不只给一个
3. **等用户主动确认**选定方案——AI 不得替用户判断，也不得先改后问
4. **确认后**：
   - 修订 `plan.md`（设计说明书相应节）
   - `decisions.md` 追加一条决策记录：背景 / 选项对比（含代价）/ 最终选择及理由
   - `tasks.md` 回退受影响任务（标 `[ ]`），列出需要新增的迁移任务
5. **同步 AGENTS.md** 若涉及技术栈或代码约定变化
6. 才开始改代码，逐任务commit，每个任务完成后停下来等用户验证
```
